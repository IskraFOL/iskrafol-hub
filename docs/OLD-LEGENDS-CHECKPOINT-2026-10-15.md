## 1. Состояние визуальной проверки

Пользователь предоставил два снимка из Minecraft с тестовой сборкой дорожных/пешеходных конструкций.

На изображениях видны:
- поднятые над рельефом мощёные секции из тёмных каменных кирпичей;
- боковые бортики и разделительные элементы;
- опоры уличного освещения с цепями и подвешенными фонарями;
- длинная прямая секция и несколько соединяемых/пересекающихся площадок;
- проверка конструкции с близкого и верхнего ракурсов.

На стыке секций на первом снимке видны незамкнутые края и перепад/разрыв между отдельными площадками. На этих двух изображениях нельзя достоверно установить, является ли это намеренным этапом сборки, тестом соединения структур или дефектом генерации. Это визуальное наблюдение для дальнейшей проверки, а не объявление подтверждённой ошибки.

Снимки зафиксированы в контексте этой контрольной точки как предоставленные пользователем материалы. В репозиторий сами изображения не загружались.

## 6. Продолжение проверки дорожного стенда — найден вероятный корневой дефект

После отдельной сверки `RoadGeom` и `Structures.place()` обнаружено конкретное несоответствие в компенсации якоря NBT-структуры при повороте на 90°.

- Для `CLOCKWISE_90` компенсация должна смещать точку по X на исходную глубину шаблона минус один.
- Для `COUNTERCLOCKWISE_90` компенсация должна смещать точку по Z на исходную ширину минус один.
- В исходной реализации оси и размеры для этих двух случаев были переставлены местами.

Это согласуется с разрывами и ступенчатыми стыками на скриншотах: `RoadGeom` рассчитывает соединения по нормализованным габаритам, тогда как общий помощник размещения мог сдвигать повернутый шаблон в другую сторону.

**Подготовлено отдельное исправление:** [PR № 9 — Fix road structure rotation anchor compensation](https://github.com/Anwite/four_old_legends/pull/9). Изменяется только `src/main/java/com/oldlegends/util/Structures.java`, две формулы четверть-поворота. PR оставлен draft и не слит в `main`.

**Статус проверки:** причина подтверждена статическим сравнением формул и согласуется с наблюдаемым симптомом, но окончательное подтверждение требует запуска мода. Сборка и игровой тест не выполнялись.

### Следующая обязательная проверка

1. Получить локально ветку PR № 9 и собрать мод.
2. В тестовом мире запустить `/legends road test` отдельно по четырём направлениям взгляда.
3. Проверить прямой → правый угол → прямой → левый угол → прямой → мост → прямой.
4. Проверить не только визуальные стыки полотна, но и бортики/фонари; после поворота отдельно проверить, не попадает ли шаблон на соседнюю площадку.
5. Если после компенсации останутся разрывы, сверить фактические размеры и точки полотна внутри файлов `road_segment.nbt`, `road_corner.nbt` и `bridge_segment.nbt` — не подбирать смещения наугад.

## 7. Повторный стенд после исправления компенсации — проблема не подтверждена как решённая

Пользователь запустил `/legends road test` и предоставил кадры с координатами. Стенд завершился, но визуально на полотне остаются подозрительные разрывы/смещения. Ключевые строки вывода:

- прямая 1: `at=[-50,-60,1] west, выход=[-51,-60,4]`
- правый угол 2: `at=[-65,-60,-6] orient=south, выход=[-58,-60,-7] → north`
- прямая 3: `at=[-63,-60,-17] north, выход=[-58,-60,-18]`

Повторная статическая сверка показывает, что вычисленные входные точки совпадают с опорными точками, которые сейчас заданы в RoadGeom. Поэтому одного дальнейшего изменения формул atFor.../exitOf... недостаточно: нужно проверить, соответствуют ли заявленным опорным точкам реальные блоки дорожного полотна внутри NBT-шаблонов.

**Статус PR #9:** открыт как draft, не слит. Изменение компенсации поворота выглядит корректным на уровне формул преобразования Minecraft, но не считается подтверждённым исправлением визуального дефекта до проверки фактического footprint NBT и игрового результата.

### Следующий этап — проверка самих NBT-шаблонов

1. Получить координаты блоков дорожного полотна в road_segment.nbt, road_corner.nbt и bridge_segment.nbt.
2. Для каждой структуры вывести диапазоны X/Z полотна на Y=0 и отдельно Y=1 для моста.
3. Проверить шесть переходов стенда по фактическим координатам блоков, а не только по точкам API.
4. После выявления несовпадения менять только подтверждённые локальные опорные точки либо размеры/поворот — без случайного подбора сдвигов.

Сборка и запуск Minecraft инструментами аудита не выполнялись; игровой результат предоставлен пользователем через скриншоты.

## 8. Дополнительная правка точек выхода углов (PR #9)

Продолжая анализ координат стенда, найдено отдельное несоответствие в RoadGeom: выход левого угла выбирал Z=15, хотя выходной рукав занимает Z=10..16 и центральная линия — Z=13; точка входа правого угла также использовала Z=10 вместо Z=13; выход правого угла использовал локальный X=7 вместо центральной линии входного рукава COR_MID_X=4.

Эти три координатных выражения исправлены в ветке fix/road-rotation-anchor-main-2026-10-15, commit 67d75adbc25f31f56a80b28c738ecfc5c9ef2cbd. Описание PR #9 обновлено. PR остаётся draft и не слит.

Это адресная правка расчётных опорных точек, согласованная с геометрией, описанной в комментариях RoadGeom. Однако сами NBT-файлы не были декодированы в карту блоков; сборка и runtime-проверка не выполнялись. Следующий обязательный шаг — запуск /legends road test и проверка стыков после углов в игре.


## 9. GitHub Actions для автоматизированного запуска Minecraft

В репозитории мода `Anwite/four_old_legends` создан workflow `.github/workflows/minecraft-client-smoke.yml` в отдельной ветке `fix/road-rotation-anchor-main-2026-10-15`.

- Коммит workflow: https://github.com/Anwite/four_old_legends/commit/2e735988ec3ddf675d267711c3aa9a89f2e36e33
- Файл workflow: https://github.com/Anwite/four_old_legends/blob/fix/road-rotation-anchor-main-2026-10-15/.github/workflows/minecraft-client-smoke.yml
- Запуски: https://github.com/Anwite/four_old_legends/actions

Сценарий запускает `runClient` в виртуальном графическом окружении Linux с Java 25 и пытается сохранить снимок экрана, лог Gradle, игровые журналы и crash reports в артефакты GitHub Actions. Это позволяет ассистенту анализировать результаты удалённого запуска без просьб к пользователю делать новые скриншоты.

**Статус:** workflow закоммичен, но успешное выполнение ещё не подтверждено. Не утверждаем, что Minecraft уже запустился, снимок получен или дорожные конструкции визуально проверены. Текущий smoke test проверяет только запуск клиента; для дорог понадобится отдельный воспроизводимый тестовый мир/сценарий.

Дальнейшие шаги: получить первый результат workflow, изучить артефакты и логи, устранить проблемы окружения при необходимости, затем автоматизировать загрузку тестового мира и проверку дорожных соединений. Все изменения мода остаются в рабочих ветках; не сливать в `main` без явного разрешения пользователя.

**Вывод:** у ассистента теперь есть возможность настраивать GitHub Actions для автоматизированных проверок Minecraft-мода; каждый успешный запуск и визуальный результат должны подтверждаться конкретными артефактами.
