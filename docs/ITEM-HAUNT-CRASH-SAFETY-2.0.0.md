# Four Old Legends 2.0.0 — сохранность предметов при «Пропажах»

**Дата аудита:** 16 октября 2026 года  
**Статус:** подтверждённый риск исходников; решение/геймплейный компромисс ещё не утверждены, изменений инвентаря пока нет.

## Подтверждено исходниками

`ItemHauntDirector.java` при снижении рассудка берёт случайный полный `ItemStack` из слотов основного хранилища 9..35. Текущий порядок:
1. `copy()` предмета, `inventory.setItem(slot, ItemStack.EMPTY)` — реальное изъятие из серверного инвентаря;
2. `pending.put(UUID, Pending(ItemStack, returnAtTick))` — **только HashMap в памяти процесса**;
3. Через 1–3 минуты возврат в близлежащий контейнер или на землю, при выходе/штатной остановке — `flush` обратно в инвентарь.

При непредвиденном убийстве процесса между пунктами 1 и 3 копия предмета не была помещена ни в SavedData, ни в другое постоянное хранилище. Последнее сохранение инвентаря игрока может уже не содержать стак — при следующей загрузке `pending` пуст. **Это реальный риск потери предметов при аварии, но ещё не воспроизведённый тестом конкретный случай.** Выход по меню, в котором `flush` обычно срабатывает, **не является доказательством** crash-safety.

## Варианты безопасной архитектуры (не утверждены)

**A — Рекомендованный для разбора: перестановка внутри одного инвентаря.** Временно переносить стек в свободный слот основного рюкзака того же игрока (без выбрасывания из PlayerData), а не в HashMap вне инвентаря. При аварии предмет останется в слоте после последнего сохранения игрока. Таймер мог бы вернуть его в исходный слот, только если тот пуст, а перенесённый стак всё ещё обнаружен; если игрок переставил предмет вручную — оставить как есть, без дублирования. Если свободного слота нет — не вызывать событие. Цена: игрок может найти вещь раньше таймера, а «нашёлся в сундуке/за спиной» придётся переработать. Перед реализацией проверить сериализацию/синхронизацию слотов и взаимодействие с инвентарём.

**B — Полностью косметическая клиентская иллюзия.** Вообще не изымать предмет сервером, а временно скрывать отображение определённого слота только на клиенте, с гарантированным восстановлением визуала при повторном входе. Безопаснее для сохранений, но требует отдельного клиентского UI/сетевого протокола и тестов совместимости GUI; сервер всегда должен хранить реальный ItemStack.

**C — Отдельный persistent escrow.** Хранить сериализованный ItemStack в сохранении, контролировать порядок записи и возврата, исключать потерю и дублирование после kill/restart. Более рискованный проект: сохранение `PlayerData` и SavedData обычно не одна атомарная транзакция, поэтому запись «изъяли из инвентаря, записали в escrow» требует протокола восстановления и идемпотентности. **Не реализовывать без полноценного теста аварийного завершения и двойной выдачи.**

## Обязательные проверки перед 2.0.0

- CI сценарий с одним специально выданным предметом, принудительным событием пропажи в отдельном тестовом мире и с полной остановкой JVM **без** штатного `SERVER_STOPPING`, затем повторное открытие сохранения.
- Сохранность при штатном выходе, одиночной и сетевой игре, полном инвентаре, смене измерения, переподключении игрока, переносе вещи самим игроком и двух одновременных пропажах.
- Проверка **количества и компонентов** исходного стека (не только названия предмета), отсутствие дублирования, корректность Container/ItemEntity при выключенных чанках.
- Сборка Java 25, реальный `runClient`, JSON-отчёт и видео/снимки. Никаких испытаний на настоящих сохранениях пользователя.

## Текущий вывод

Риск высок: текущий `pending` не переживает crash. Пока не утверждён способ безопасного сохранения предмета, **не объявлять существующую механику безопасной**. Не отключать её молча и не переписывать под видом косметического исправления без отдельного технического решения.

## Решение КТ-2026-10-16 / ITEMHAUNT-SAFE-01 — исправление слито

**Основная ветка Minecraft-мода:** `main=8594d4c16c1b37c7e35bd51088c5af9ce0fa9643`, [PR #47](https://github.com/Anwite/four_old_legends/pull/47) **merged**.
