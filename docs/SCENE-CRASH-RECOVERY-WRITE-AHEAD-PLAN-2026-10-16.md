Это помечает данные для будущего сохранения, **не гарантирует синхронную запись перед заменой блока**. Переносить старый механизм целиком небезопасно.

## Требуемые инварианты

1. **Сначала надёжно зафиксировать снимок, потом менять мир.** До первой замены блока полный набор исходных `BlockState` для площадки и идентификатор сцены должен оказаться на диске с подтверждением записи. Если это не удалось, сцена не стартует.
2. **Один журнал на сессию сцены**, а не 4291–5671 отдельных немедленных файловых сохранений. Запись всего снимка ограничена по размеру/времени, проходит атомарно настолько, насколько позволяет проверенный API файловой системы; детали подтверждаются отдельно для Minecraft 26.3.
3. **Идемпотентное восстановление.** У записи есть `dimension`, `position`, `originalState` и `expectedTemporaryState` (или эквивалентный проверяемый признак). Если текущий блок уже исходный — засчитать как восстановленный. Если текущий блок совпадает с временным блоком сцены — вернуть исходный. **Если текущий блок отличается от обоих, не перезаписывать его молча**: оставить конфликтную запись, зафиксировать сообщение и запросить отдельное решение.
4. **Не стирать чужие block entities.** Проверять отсутствие контейнеров/сущностей блоков до и непосредственно при замене; не восстанавливать один лишь BlockState поверх сундука с инвентарём.
5. **Нет принудительной генерации чанков.** Восстанавливать только загруженные чанки, оставлять записи в очереди до повторной загрузки, ограничить число обрабатываемых блоков за тик.
6. **Нет вечного спама в журнале.** Ошибочные ключи/кодеки и невозможные позиции логируются с ограничением частоты и помечаются как требующие ручной проверки. Они не должны бесконечно проходить горячий цикл `onServerTick`.
7. **Не очищать журнал до подтверждённого возврата.** Удаление записи и дисковая фиксация этого удаления должны иметь определённый порядок; внезапный обрыв в любой фазе не должен привести к слепой повторной замене блоков.
8. **Старый мир не переписывается при ошибке чтения журнала.** Невозможность восстановить данные переводит механизм в безопасный запрет новых сцен; не создаёт пустой журнал поверх проблемного.

## Схема двухфазного жизненного цикла

- `PREPARING`: проверка площадки, блок-сущностей и полной загрузки области, снимок исходных блоков без модификации мира.
- `PREPARED`: полная запись снимка на диск подтверждена; только после этого допустим переход к строительству.
- `ACTIVE`: временная сцена построена. Во время работы сохраняется идентификатор ожидаемых временных блоков; другие сцены не должны пересекаться с занятым объёмом.
- `RESTORING`: постепенно возвращать блоки с проверкой результатов, сохранять нерешённые записи и коллизии.
- `COMPLETE`: исходные состояния подтверждены; журнал завершён, освобождён для следующей сцены.

**Открытый вопрос реализации:** какой именно путь синхронного, проверяемого и атомарного сохранения доступен в Minecraft 26.3 / Loom 1.17.18 (NBT SavedData API против отдельного временного файла с безопасной заменой). До ответа на него нельзя выдавать `setDirty()` за durable write-ahead log.

## Приёмочные испытания: только одноразовые миры GitHub Actions

| Момент искусственного сбоя | Ожидаемое поведение после повторного запуска |
|---|---|
| До подтверждённого сохранения `PREPARED` | Мир вообще не изменён |
| После сохранения `PREPARED`, до первой замены | Безопасное завершение журнала, никаких потерянных блоков |
| После частичного построения (например 30%) | Все подтверждённые временные блоки восстановлены |
| Посреди `RESTORING` | Следующий запуск завершает откат, не создаёт дубликатов дропа |
| После возврата блоков, но до удаления журнала | Повторный откат идемпотентен |
| Незагруженный чанк | Запись ожидает загрузки без генерации чанка |
| Повреждённый codec / отсутствующий registry ID | Конфликт сохранён, новые сцены заблокированы, журнал не стёрт |
| Другой блок поставлен игроком во время восстановления | Блок игрока не перезаписан; запись отмечена конфликтной |
| Место с сундуком или block entity | До строительства сцена отклонена без изменения контейнера |
| Мир A → мир B → мир A в одной JVM | Журнал каждого мира остаётся строго изолированным |

Дополнительная проверка: сравнить **весь исходный объём** по `BlockState` и данным поддерживаемых block entities до/после. Отсутствие записей во внутреннем `Map` само по себе PASS не даёт.

## Кодовый аудит 16.10.2026 после исправления ItemHaunt — новые точные риски

Проверены **текущие** исходники `main=8594d4c`: `src/main/java/com/oldlegends/event/LegendaryMeetingEvent.java` и `LikChroniclerEvent.java`.

- **Хорошо:** обе сцены проверяют **загруженность чанков и отсутствие block entities** во всём цилиндрическом объёме до начала строительства (`isSafeChamberSite()` и `isSafeArchiveSite()`). Также отменяют запуск, если `allowGriefing=false`. Это сохраняем, а не переписываем вслепую.
- **Высокий риск по умолчанию:** в `LegendConfig.java` параметр `allowGriefing = true`. Таким образом, механизм запрета сцен существует, но без изменения настройки по умолчанию **не активен**. Это не равнозначно защите от краша.
- **Критичная последовательность:** `setTemporaryBlock()` сначала записывает `originalBlocks.putIfAbsent(..., level.getBlockState(...))` только в **static Map** и тут же выполняет `level.setBlock(...)`. Никакой подтверждённой долговечной записи снимка до изменения блоков нет.
- **Отдельная ошибка отката в исключительной ситуации:** методы `restoreChamber()` и `restoreArchive()` ловят `Throwable` для отдельных блоков, ведут счётчик `failures`, но в конце **безусловно вызывают `originalBlocks.clear()`**, даже если часть блоков не была восстановлена. `setBlock(...)` возвращает boolean, однако этот результат вообще не учитывается. Таким образом, информация о неудавшихся блоках может быть потеряна даже **без** краша, если откат идёт с ошибками.
- **Конфликты с действиями других игроков:** восстановление выполняется без сравнения текущего блока с ожидаемым временным значением. Если другой игрок успел изменить участок сцены, `restore*()` может слепо перезаписать его изменение. Требуется отслеживать *финальное* временное состояние для каждого положения (учитывая, что позиции пишутся несколько раз) и **оставлять конфликтный блок нетронутым**.
- **После аварии:** `resetForServer()` стирает статические карты; на следующей загрузке нет исходных состояний, из которых можно выполнить ремонт. Штатные 0 несовпадений на 4,291 + 1,380 блоках не покрывают этот сценарий.

**Следующий PR не следует сразу сливать в main.** Сначала смоделировать откат с частичной ошибкой и чужим блоком, с явными машинными инвариантами `restored`, `conflicts`, `failed`. Затем подготовить долговечный write-ahead-журнал, записываемый и подтверждаемый **до** замены блоков; отдельно доказать физическое восстановление после убийства JVM. Никаких предположений, что один вызов `setDirty()` сам по себе достаточен.

**Защита на время аудита:** `/legends config set allowGriefing false` блокирует построение обеих сцен в текущем коде (в том числе ручной запуск), но может также повлиять на другие мировые события мода. Это осознанный временный компромисс, а не постоянное решение.

- **Новый обязательный дизайн перед интеграцией:** каждый сценарий должен *без физической модификации мира* построить полный deterministic blueprint; собрать `original` и `expected` конечные `BlockState` (учитывая многократную запись координат), проверить loaded-чунки и отсутствие BlockEntity/коллизий другой сцены, затем создать WAL и дождаться подтверждения. Только после этого разрешить `setBlock`.
- **Открытые вопросы безопасности:** путь WAL должен принадлежать конкретному save-root; при начале загрузки мира требуется сначала обнаружить unresolved WAL и заблокировать новые сцены, а позже идемпотентно восстановить лишь совпадающие с `expected` блоки. При несовпадении сохранить конфликт, не удалять журнал; физические state и NBT block entities проверять отдельно. `force(directory)` может быть недоступен под Windows/некоторыми FS — до проверки должно быть fail closed.
- **Не вливать в main** до игровых fault-injection тестов (save/quit, kill -9, stale WAL, повреждение, повторный restart, блок игрока, A→B→A) и строгого сравнения всех позиций после реального повторного входа. Наличие CLI проверки двух JVM НЕ доказывает защиту сохранения чанка при crash.
