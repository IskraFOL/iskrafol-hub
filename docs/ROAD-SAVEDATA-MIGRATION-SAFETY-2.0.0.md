# Four Old Legends 2.0.0 — план безопасной совместимости дорожных сохранений

**Дата:** 16 октября 2026  
**Статус:** план аудита, **никакая миграция не реализована и не утверждена к релизу**.

## Подтверждённые свойства текущего кода

- `ArgSavedData` (Minecraft 26.3) использует SavedData Codec с optional-полями `roadEnds` и `roadOccupied`. `ArgState.importRoads` загружает строки через `RoadNetwork.importFromKeys`.
- `RoadEnd.fromKey` принимает старые ключи из **4 частей** (`x,y,z,direction`) и новые из **6 частей** (`x,y,z,direction,runLength,lastTurn`), но координаты сохраняет без преобразования. Поля истории для 4-частной формы возвращаются к нулю.
- Поскольку геометрическая семантика `RoadEnd.pos` уже менялась ранее, даже наличие шести частей **не доказывает**, что координата рассчитана новым алгоритмом. Версия дорожной геометрии в SavedData явно **не маркируется**.
- Физические блоки уже построенной дороги хранятся в чанках независимо от `RoadNetwork`. Удаление `roadEnds`/сброс `roadOccupied` не откатывает существующие сооружения и может породить разрывы или наложения при повторном посеве.
- При штатном `SERVER_STOPPING` вызывается `ArgSavedData.copyFrom`, а каждые 2400 серверных тиков происходит дополнительное копирование. Данные старого мира нельзя безопасно менять без отдельного архива.
- В удалённом CI [run 38901080354](https://github.com/Anwite/four_old_legends/actions/runs/38901080354) обнаружен файл `run/saves/FOL_CI_RoadProbe/dimensions/minecraft/overworld/data/oldlegends/arg_state.dat`, размер **204 байта**. Корректность восстановления пока проверяется в draft [PR #17](https://github.com/Anwite/four_old_legends/pull/17).

## Минимальный безопасный протокол

1. **Свежая схема, без миграции:** создать отдельный мир, естественно вырастить несколько сегментов, сохранить через меню, загрузить тот же мир; убедиться, что сохранены все ключи концов, число занятых клеток, напряжение и отсутствие дублирования. Затем повторить после **полного холодного перезапуска JVM**.
2. **Старый формат строк:** сформировать синтетический fixture четырёх- и шестикомпонентных ключей. Убедиться, что парсер их принимает, но **не выдавать** результат за геометрически правильную миграцию.
3. **Копия исторического мира:** для настоящей миграции понадобится доказанный пример сохранения старого алгоритма вместе с его чанками. Тесты должны выполняться только на копии, предварительно сохранять хэши оригинальных файлов.
4. **Версионирование:** при проектировании миграции добавить явное поле типа `roadGeometryVersion` с backward-compatible значением по умолчанию и хранить его вместе с `roadEnds` / `roadOccupied`. Саму схему и значения версий **согласовать отдельно** до изменения кода.
5. **Сохранить текущие блоки:** не удалять существующую сеть при невозможности однозначно определить старую геометрию; лучше остановить только потенциально опасное продолжение и выдать понятную диагностику, чем строить с разрывом. Перед таким поведением потребуется отдельное ТЗ.
6. **Регрессия:** запуск на новых мирах, повторный вход/выход, восстановление после падения клиента, частично повреждённые данные, незагруженные чанки, четыре направления дороги и оба типа концов; сравнить поведение до/после.
7. **Релиз:** слияние PR только после утверждения, тестов и локальной проверки на копии мира; не менять данные реальных игроков автоматически при первом запуске непроверенной миграции.

## Что нельзя утверждать пока

- Не доказано, что любой мир от версии 1.2.0 уже содержит реальные дороги со старой геометрией.
- Не доказано, что старые 6-польные ключи соответствуют корректной новой системе.
- Не доказано восстановление после аварийного убийства JVM и отсутствие потерь между периодическими снимками состояния.
- Нельзя считать готовность debug-стенда доказательством совместимости исторических миров.
